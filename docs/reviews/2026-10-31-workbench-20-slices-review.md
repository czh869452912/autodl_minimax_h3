## 1. 结论

**整体方向正确，适合继续演进现有底座；当前最需要的是跨切片契约收敛。**

20 个切片没有把问题转移到新聊天壳或外部执行平台。完整媒体提交、分页、项目 Skill、版本化设定、计划暂停/重做、范围与运行规格均沿现有共享命令、SQLite、CAS、预算和执行器展开；没有在本次差异中发现新增桌面/远端 Worker。这符合用户明确约束。

但“每个切片有测试”尚未证明这些功能合起来行为正确。本轮发现一个优先修正的授权范围问题，以及五项可复现的引用/编辑/恢复设计问题。它们集中在新增对象与旧底座的连接处，说明下一轮应先横向打通引用、授权、版本审阅和失效语义，再扩展更多节点或角色。

不建议推翻已有实现，也不建议直接把 20 个切片视为综合工作台已经闭环。当前是从可靠生成工具向项目生产系统推进的中间阶段。

## 3. 六项需要调整的问题

### R1 / P1：用户授权某个计划，实际创建了通用项目额度

**触发与后果：**用户在计划页确认“此计划”“使用计划提示词”“固定输入版本”“仅授权一次”，但产生的授权没有绑定该计划、步骤或准备请求。同项目的其他生成请求可以先预留这一次额度，目标计划随后因额度不足阻塞。这里存在授权对象与实际可执行范围的不一致，不只是余额显示问题。

证据链：

- [ProjectPlans.tsx:38](../../mobile/src/creative/ProjectPlans.tsx) 展示特定计划的确认；[第 46 行](../../mobile/src/creative/ProjectPlans.tsx) 创建 project/provider/operation 级 grant，没有 requestBinding 或计划约束。
- [budget.ts:23](../../mobile/src/creative/budget.ts) 将此 grant 纳入通用授权摘要，Agent 可通过 creative_context 得到它。
- [budget.ts:53](../../mobile/src/creative/budget.ts) 仅在已有请求绑定时检查 command/hash；未绑定 grant 允许同项目其他请求预留。

**本轮复现：**真实 SQLite 中创建计划、选择候选、进入等待授权、按计划页同样字段建立 grant 并 resume；授权出现在通用摘要；用无关 command/hash 成功预留，剩余次数变为 0。没有创建真实外部请求，更没有实际扣费记录。

项目级通用额度本身可以是一种产品能力，但必须由用户明确授予。该问题不能通过把计划卡改成含糊的“授权项目”来掩盖；此处意图显然是具体计划。

**建议：**计划授权至少固定 plan/step/draft/revision，并在准备实际请求后绑定 canonical hash，或者直接复用已经完成的请求绑定确认机制。预留和派发都验证其目标；计划专属 grant 不出现在通用 Agent 授权列表。通用项目 grant 保留独立入口与清楚语义。

**验收：**给计划 A 的一次授权不能被草稿 B 或计划 B 使用；取消/变更/重新准备后旧授权不能扩大范围；原任务重放仍幂等；额外授权失败不能留下可被无关请求消费的额度。

### R2 / P2：设定的素材引用尚未纳入使用关系与生命周期

**触发与后果：**素材作为已采用角色设定的参考并绑定镜头后，仍可以从项目移出，再放进回收站；使用关系页可能显示无引用，而设定和镜头保留这个版本 ID，语义 stale 仍为 0。用户得到的是一条表面正常、实际资源已经脱离当前可用范围的依赖。

证据链：新增引用位于 [semanticResources.ts:44](../../mobile/src/creative/semanticResources.ts)；[service.ts:213](../../mobile/src/creative/service.ts) 的项目解除引用只额外检查封面；[assetLifecycle.ts:24](../../mobile/src/creative/assetLifecycle.ts) 的回收站保护和 [usageGraph.ts:5](../../mobile/src/creative/usageGraph.ts) 都未包含 semantic references。

**本轮复现：**创建参考图→设定引用→采用→绑定镜头→移出项目→usage 返回空→回收站成功；semantic reference 行保留，shot semantics 返回 stale:0。这不是物理文件已被清除的证明，而是引用治理与可用性事实不一致。

**建议：**把语义版本引用接入统一依赖查询、删除/移出保护和可用性诊断，区分“上游设定更新”和“参考资源不可用”。明确当前使用与历史保留策略：不要简单地永久禁止一切历史引用资源的管理，也不能悄悄留下不可解释的悬空依赖。资源管理动作应指出受影响设定/镜头，并走明确的解除或替换流程。

**验收：**上述正常用户路径要么被带具体引用信息地阻止，要么经显式依赖处理完成；usage 能追溯设定版本；缺失、回收站和跨出项目范围不会被质量诊断当成完整有效依赖。

### R3 / P2：镜头设定只有绑定，没有解除，8 项上限会形成死路

当前 [semanticSchemas](../../mobile/src/creative/semanticResources.ts) 提供 create/revise/adopt/bindShot，没有 unbind。绑定表按 shot/entity 定位，[第 28 行](../../mobile/src/creative/semanticResources.ts) 限制 8 个身份；同一身份可以换版本，但错误身份不能移除。界面也没有解除操作。

**本轮复现：**依次绑定 8 个不同身份，第 9 个失败；调用解除命令返回 UNKNOWN_CREATIVE_COMMAND。用户错绑或故事改写后只能保留错误依赖，严重时被迫重建镜头。

**建议：**增加用户控制、带 expectedShotRevision 的解除/替换命令；替换可以一次事务移除旧身份并绑定新身份。历史草稿/Job 快照保持不变，后续计划按实际依赖变化提示重新确认。不要通过取消上限来替代可逆编辑能力。

**验收：**误绑能解除；满额能原子替换；过期 revision 拒绝；已提交输入和已采用成果不被改写；删除绑定后可在活动记录中解释变更。

### R4 / P2：采用或绑定会清空同页尚未保存的设定修订

设定页把版本审阅、绑定和新版本编辑放在同一状态容器。[SemanticResourcesScreen.tsx:30](../../mobile/src/creative/SemanticResourcesScreen.tsx) 的通用 execute 在任何成功命令后清空 content/title/referencesDirty，并重新 choose；采用与绑定按钮直接调用 execute，没有先处理编辑区脏状态。

**本轮组件复现：**选择设定→输入未保存修订→采用一个已保存版本→未调用 leave guard，输入变为空。当前已有 useUnsavedChanges 不能保护这条同页操作路径。该结论来自组件状态测试，未做本轮设备点击复现。

**建议：**将“正在编辑的版本草稿”与“查看/采用/绑定的历史版本”分开；非保存动作不能无条件重置编辑内容。需要切换对象或丢弃时走保存/保留/放弃决策，采用不相关版本也可保留当前编辑缓冲。

**验收：**编辑文字和参考素材后采用、绑定、切设定、返回，均不会无提示丢失；保存失败保持输入；保存成功仅清理已提交的对应编辑会话。

### R5 / P2：用整个镜头 revision 代替输入依赖，会把排序变化当成生产失效

[story.ts:49](../../mobile/src/creative/story.ts) 重排时为所有镜头增加 revision；[planDispatch.ts:18](../../mobile/src/creative/planDispatch.ts) 对镜头 revision 做全等检查，不匹配就要求取消旧计划。

**本轮复现：**创建计划并选图→只调整镜头顺序，保持参考和 Prompt 不变→提交栅栏拒绝。当前代码即使传入相同排序也会更新 revision。20 个独立镜头批次因此可能在一次普通排序后一起变成需要取消重建的对象。

这是保守阻断策略，不是擅自使用旧输入的漏洞；问题在于阻断范围过大，而且恢复操作过重。安全栅栏应该保留。

**建议：**保留 revision 处理编辑并发，同时增加生产依赖签名/单独 inputRevision，覆盖实际参考、语义版本、Prompt/规格和 workflow 等。排序/显示标题等不影响该节点输入的变化不使节点失效。真实输入变化则进入可审阅的重新准备流程，保留尝试和审计，不只有取消重建。

**验收：**纯重排不重新授权或生成；换图/改实际请求/重绑设定会重新准备；准备与提交之间的竞争仍被拒绝；旧 Job 回执不被新栅栏破坏。

### R6 / P2：设定版本的“审阅、采用、绑定”依赖不完整的历史列表

[SemanticResourcesScreen.tsx:29](../../mobile/src/creative/SemanticResourcesScreen.tsx) 仅加载最近 20 个版本，没有版本分页；[第 41 行](../../mobile/src/creative/SemanticResourcesScreen.tsx) 又仅在这份列表中遇到 current_version_id 时渲染绑定按钮。

**本轮组件复现：**v1 已采用，随后有 v2–v21 待审；列表正常返回最近 20 项时，不再出现任何“绑定到镜头”操作，虽然 v1 仍然是有效采用版本。不能要求用户先采用一个新版本才能继续使用旧的已批准设定。

同一页还有相关审阅缺口：版本卡显示正文，引用编辑区加载的是当前采用版本的引用，未提供所选待审版本的完整参考清单/预览。采用时无法就近核对该版本实际绑定了哪些图或声音。列表有“显示最近20”说明，但说明不能代替核心操作的可达性。

**建议：**实体详情始终独立读取/展示当前采用版本；历史候选有游标和版本详情；每个详情包含正文、完整参考版本、用途和可用性，随后才采用/绑定。版本列表截断不能决定核心操作是否存在。该模块的读取应放入统一服务契约，减少页面自行拼 SQL 导致的缺项。

**验收：**超过 20 个版本仍可读、采用、绑定指定旧版本；待审版本的参考能完整核对；加载失败不沿用另一版本引用；核心操作不依赖列表是否包含当前版本。

### 还需要作出的系统设计选择

**D1：批次现在是原子“建计划”，还没有形成用户可管理的制作批次。**

批次成员已持久化，但当前产品读取未利用 batch/membership 来提供批次视图、选择范围、批次摘要或恢复入口。按钮自动取前 20 个有图/描述的镜头，而非让用户勾选；每个镜头还需重新确认已经采用的图片及单次授权。计划列表只读最近 30 条，没有继续读取入口。

这些限制不使现有批次事务错误，但意味着不能以此宣布“20 镜头生产”闭环。建议补：明确选择镜头、批次成员与总览、只处理未完成/失败项、范围明确的批次额度及逐步预留、保留逐镜审阅。独立镜头先做稳即可，不要求先实现任意 DAG 或复杂低代码画布。

**D2：设定快照目前是本地追溯，不是执行约束。这个分离正确，但产品需要把二者接起来。**

当前 [draftSemantics.ts](../../mobile/src/creative/draftSemantics.ts) 冻结创建时语义，[videoSubmission.ts:74](../../mobile/src/creative/videoSubmission.ts) 放在展示上下文，归档已修正为不污染 recipe.input。保留此分离，不要为“让设定生效”重新把本地元数据混入供应商参数。

下一步需要显式记录：哪些设定只是背景资料、哪些被编入 Prompt、哪些参考实际进入供应商槽位、哪些规则只能事后检查。应有准备结果和用户可审阅的“本次如何使用设定”。新设定不能自动上传其中所有素材；外发许可与任务能力协商仍未实现。这是核心能力缺口，不是已经证明模型忽略设定的运行结论。

**D3：RunSpec 是一致性栅栏，尚不是完整运行契约。**

[runSpecification.ts:8](../../mobile/src/agent/runSpecification.ts) 固定配置及工具名，[skills/runtime.ts:32](../../mobile/src/agent/skills/runtime.ts) 提供的主要是创作工具清单；文件系统、todo、潜在 task 等框架工具不在这份业务工具快照中，也没有统一副作用/版本/输出契约及累计预算。应用重启后任意认知轮次精确续跑的问题仍未被这两张表解决。

建议先抽出同一来源的 ToolPolicy/有效能力集合，实际 graph 和快照都从它构造；增加整轮调用/token/时长、子任务汇总和错误分类，沿现有 Job/Plan 建立检查点。不要为了“完整 RunSpec”先建设大量角色，也不要只不断增加配置 JSON 字段。

**D4：已有文档对未完成范围的表述总体诚实，应继续保留。**

未完成的端口能力目录、独立素材外发许可、通用节点、感知质检和本地后期，不应因为本轮切片数量多就改称完成。优先用一条多对象实际流程验证相互作用，比继续累加“已实现功能数”更有意义。

## 5. 下一阶段建议

建议下一轮围绕三个收敛工作包推进，而不是直接启动更多平行功能：

1. **授权闭环**：先修 R1，将计划/批次授权纳入请求或步骤绑定；同时覆盖暂停、取消、准备失败、过期、未知结果下的额度归属。保留明确未知费用次数控制，不虚构金额保证。
2. **设定闭环**：统一引用查询与保护，补解除/替换、候选详情、历史分页和编辑缓冲保护，集中解决 R2/R3/R4/R6。随后设计显式的设定→请求绑定方式和外发范围。
3. **生产闭环**：将 revision 并发控制与依赖签名分开，解决 R5；用批次总览、选定镜头和部分恢复打通有限多镜头流程。补 Android 前后台/进程恢复验证，不引入任何外部 Worker。

推荐验收场景：已有角色设定和参考→修订待审→核对版本参考后采用→绑定两个镜头→解除一次误绑→准备有限批次→授权→只调整镜头顺序→只让真正改变输入的步骤重新准备→模拟一个任务确定失败→显式重做→保留原费用与采用版本→应用重启后恢复。测试应同时检查 UI 意图和数据库/请求边界。

## 6. 证据限制与最终判断

本轮六项现象均有代码定位，其中四项由真实 SQLite 离线执行复现，两项由组件状态复现。没有证明发生真实错扣费用、物理原件丢失或设备 UI 验收失败。P1 授权问题应优先修复，其余 P2 属于引用治理、编辑可逆性、核心操作可达性与失效范围问题。

桌面/远端 Worker 仍是禁止项；Android 生命周期限制应通过持久小步骤、暂停原因和恢复核查解决。保持现有底座，先消除上述跨模块不一致，再扩展更多创作能力，是当前更稳妥的推进方向。
