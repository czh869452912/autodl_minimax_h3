# 掌上智能 AI 创作平台 UX/UI 交互架构专题研究报告

**项目：** `czh869452912/autodl_minimax_h3` · `codex/creative-app`  
**代码基线：** `85c29c02b106c64b1cb0db5e915b643493504880`（2026-10-28）  
**报告版本：** V1.0 · 2026-10-28  
**定位：** 移动产品交互专项评估 / 设计决策 / 增量改造建议

> **核心结论**：不要再通过缩小按钮、增加 Tab 或堆叠 Sheet 承接功能增长。保持现有“手工 / Agent 双工作方式”作为过渡基础，将产品组织单位从“功能模块”转向“当前创作焦点”，建立统一的 **焦点（Focus）—意图（Intent）—工作表面（Surface）—返回（Return）** 交互契约。手机上只显露当前对象的高频动作，复杂能力以可恢复的上下文工具进入。**先改交互流，不改执行内核；先做纵向样板，不全局换皮。**

## 执行摘要：六项最重要的判断

1. **真正的瓶颈是“上下文与注意力”，不是功能数量本身。** 项目、镜头、资产、草稿、任务、会话以及结果版本都有合理的数据意义，但用户不应在一次创作操作中反复理解这些内部实体。
2. **已有界面并非没有设计。** 现有分支已实现双工作台、图片画布与编辑抽屉、视频创作/结果切换、候选结果、任务角标、参数 Sheet、Agent 活动收敛、草稿与版本保存保护。应保留并统一这些积累，而不是再次推倒重做。
3. **采用“稳定位置 + 情境内容”，而非不可预测的全动态 UI。** 主操作放在稳定区域，随对象的制作阶段显示不同动作；同时让用户始终能找到完整能力目录与高级编辑入口。
4. **“从镜头发起生成”与“独立快速生成”必须共存。** 二者进入同一张草稿/生成工作台；前者携带项目、镜头、参考版本和返回目的地，后者保持无项目门槛。
5. **资产管理必须成为交互中的隐性基础设施。** 选择资产应像选择照片一样自然；版本固定、生成来源、项目引用应由系统处理并在关键决策点解释，不能把数据库关系操作一一暴露为按钮。
6. **UX 改造必须同时约束性能。** 仓库 2026-10-28 性能审计已报告版本全量轮询、详情逐版本校验、非虚拟化媒体列表等增长风险。界面再简洁，如果几百个版本下选材、审阅卡顿，仍无法成为长篇制作工具。

**推荐的第一交付物**：以一个项目镜头为起点，完成「选定参考图 → 调用 H3 视频工作台 → 提交 → 在原镜头审阅候选 → 采用 TAKE → 回到镜头」的无上下文丢失闭环，同时保证独立的 NovelAI 快速出图不受影响。

## 2. 现有分支的真实 UX 基线与结构性问题

### 2.1 已具备的可保留资产

- **双工作方式**：`mobile/src/ui/WorkbenchModeSwitcher.tsx` 已把“手工/Agent”放入顶部模式选择，而不是新增永久底栏；主 Tab 的视觉入口已隐藏（`mobile/app/(tabs)/_layout.tsx`）。这是值得延续的收敛结果。
- **独立创作循环**：`CreativeHome.tsx` 在同一工作台恢复图片/视频草稿；`ImageDraftScreen.tsx` 使用画布与 `ImageEditorDrawer`；`VideoDraftScreen.tsx` 提供创作/结果状态切换。
- **持久制作状态**：`ProjectShots.tsx` 已能依据镜头是否选图、已有草稿、选定视频来提供不同的主操作；`CreativeResults.tsx` 可展示真实候选与来源。
- **复杂编辑按需唤起**：`WorkbenchUI.tsx` 已有 `ParameterSheet`、`InlineWorkbenchPanel`、`SegmentedChoices`；不是要从零引入 Sheet。
- **可靠性**：草稿自动保存、预提交冻结、未知结果核查、采用引用显式变更、Agent 审核/授权已有相应路径，禁止为了 UI 改造绕开这些机制。

### 2.2 代码级证据与风险矩阵

| 观察位置 | 当前行为（源码依据） | UX 影响 | 本报告判断 |
|---|---|---|---|
| `CreativeHome.tsx` 约 71–78 行 | 顶部同时放模式切换、图片/视频选项、新建、创作记录、任务、设置 | 工作尚未开始，顶栏已承担多个层次的职责 | P0：标题栏整合，不再继续追加操作 |
| `CreativeWorkspace.tsx` 约 38–64、129–215 行 | 一个容器持有项目/素材/编辑/管理/版本/处理/导入/回收等多种状态并由条件分支渲染 | 增量功能容易增加状态组合，回退与入口来源难以统一 | P1：拆成对象页和共享表面，不立刻改数据库 |
| `ProjectShots.tsx` 约 60–78 行 | 每个镜头有文本描述、一个阶段主操作和“更多镜头操作” | 行为已有阶段意识，但需要“看到镜头”并逐条操作，缺少真正的镜头焦点页 | P0：镜头卡→焦点页样板 |
| `VideoDraftScreen.tsx` 约 211–243 行 | 视频有“创作/生成记录”标签，且工作流、输入、参考、价格、多个 Sheet 并列 | 同一生成器的入口/结果切换属于必要模式，但跨镜头跳转仍可能中断创作心流 | P0：支持来源与返回上下文 |
| `ImageDraftScreen.tsx` 约 207–225 行 | 画布、编辑抽屉、助手、处理工具、历史、底部生成区共享可视空间 | 当前已接近移动绘图工作台，但多个编辑表面存在调度和空间竞争 | P0：定义工具表面互斥与键盘策略 |
| `CreativeResults.tsx` 约 159–212 行 | 成果上有保存/信息/增强/放大/用于镜头/更多/历史等入口 | 用户很难辨别当前主目的；“仅预览、选定、继续生成”语义可能竞争 | P1：用生成意图决定主操作，其他进入分组工具 |
| `WorkbenchUI.tsx` | Compact 模式中部分图标尺寸降至 34dp，文本按钮压缩为 36dp | 视觉密度增加，但命中区与可发现性可能受损 | P0：先减控件，再按 44–48dp 可点击区验收 |
| `docs/reviews/2026-10-28-performance-audit.md` F03–F08 | 版本轮询、逐条文件校验和媒体全量挂载存在规模风险 | 长篇创作资产越多，操作越不流畅 | P0/P1：UI 虚拟化与批量摘要查询同步推进 |

重要的是：这里的“风险”不等于已复现的真实误操作。用户感知的具体严重程度仍需要录屏、触控数据与真机测试。现有分支过去几轮 UX 改动已改善了部分问题，不能把旧审计中的过时现象直接当成现状。

### 2.3 五类根因（比页面数量更本质）

1. **对象切换成本**：从镜头跳至生成草稿，再进全局任务/素材，再回镜头；操作路径跨多个数据概念，返回上下文容易不透明。
2. **工具暴露成本**：当前工作台功能增长以按钮/菜单/Sheet 的数量为主要载体；“所有功能都能找到”不等于“高频功能易于到达”。
3. **模式冲突成本**：手工与 Agent 是工作方式，项目/资产是创作对象，图片/视频是生成能力。若把三者当作同等级导航选项，用户会不断回答“我该进入哪个模块”。
4. **空间竞争成本**：媒体预览、文本输入、候选条、结果操作、AI 对话、键盘和安全区，在 360–400dp 宽屏幕上争抢同一个视口。
5. **异步认知成本**：生成成功、素材归档、保存到相册和镜头采用属于不同进度，不能简单用一个“成功/失败”切换整个页面。

这些根因解释了为什么继续压缩边距或再加一层菜单只能暂时缓解问题，却不能让系统长期承接角色设定、分镜、粗剪和 Agent 制片功能。

## 3. 成熟产品能借鉴什么，不能借鉴什么

| 来源 | 经官方资料确认的设计思想 | 手机可迁移原则 | 不应照搬的部分 |
|---|---|---|---|
| LTX Studio | 从剧本/概念进入分镜、生成、时间线，同一工程连接不同阶段 | 工程与镜头连续性，制作阶段可回溯 | 桌面多栏、完整 NLE 工具条；其官网明确推荐桌面使用 |
| Higgsfield Cinema Studio | Director Panel、可复用 Elements、AI Director 调整摄影参数；生成仍需用户确认 | 把专业控制收成“导演设置”，Agent 提建议、用户确认执行 | 同屏展示全部摄影参数或照搬其专有模型选项 |
| InvokeAI（7 系） | Gallery / Canvas 目的地明确；结果先进入 staging，再采纳或保留 | “候选托盘→对比→采用”；每次提交冻结输入和目标 | 直接移植画布/节点编辑器到手机 |
| Adobe Photoshop | Contextual Task Bar 随选中对象提供相关操作 | 在对象附近提供少量直接动作，减少跨面板搜寻 | 将桌面悬浮工具条原样叠加在手机媒体画面上 |

## 4. 信息架构方案比选：不要贸然改成三四个底部 Tab

有三种可选方案：

| 方案 | 特点 | 长处 | 代价/风险 | 判断 |
|---|---|---|---|---|
| A：继续按功能加入口 | 创作、项目、资产、Agent、分镜等独立入口 | 直观、实现简单 | 功能增长直接挤压导航；跨模块交接多 | 不推荐作为长期模式 |
| B：彻底改成“工作台/资源库/助手”三大 Tab | 简化入口，常驻底部导航 | 对新用户可能容易理解 | 与当前已实现的双工作台冲突；全屏创作仍要隐藏底栏；改动与验证成本较高 | 不建议现在整体切换 |
| C：保留双工作方式 + 对象焦点 + 上下文能力调用 | 顶级区分手工/Agent；项目与素材为可进入对象；从对象调用能力 | 与现有代码连续，便于逐步验证；更适合多阶段制作 | 需要统一返回协议、动作规范、表面管理 | **推荐** |

### 4.1 推荐层级

```text
应用启动 → 恢复上次工作 / 快速创建
 ├─ 手工工作方式（图片 / 视频生成，可无项目）
 └─ Agent 工作方式（项目对话，可进入具体创作对象）

共享对象入口：项目 / 镜头 / 素材 / 创作记录 / 任务
   └─ 当前焦点：某个 Shot、AssetVersion 或 Draft
       ├─ 查看与选择当前内容
       ├─ [本阶段主操作]
       ├─ 工具抽屉：参数 / 参考 / 版本 / 更多
       └─ 上下文 Agent：建议 / 草稿 / 审核

结束工具操作 → 原焦点与视图位置恢复
```

“双工作台”是**工作方式**，不是要求用户在每一步先选一次“手工还是 Agent”。例如在镜头中点“帮我修改运镜”，应直接唤起当前镜头的 Agent 面板，而不应强制回到 Agent 首页重新选项目。

### 4.2 主层级的明确规则

- **全局首页/手工工作台**：最近工作 + 直接生成，不强制建立项目。
- **项目页**：进度、下一步和镜头，不承担长参数编辑。
- **镜头焦点页**：画面、制作意图、参考、候选、采纳，承担主要制作动作。
- **素材库**：检索和选择，是可复用能力，不是每次生成后必须访问的中转站。
- **任务入口**：用于跨任务查看和异常处理，普通完成通知应能直接回到当前草稿或镜头。
- **Agent 全屏**：长对话、规划和跨项目探索；**上下文 Agent**：针对当前镜头/草稿/素材的短任务。

## 5. 统一交互契约：Focus — Intent — Surface — Return

这是本报告最重要的技术与产品设计建议。它不是增加一个庞大的 UI 框架，而是让各页面遵守同一套“操作从哪里来，改变了什么，操作后去哪里”的规则。

### 5.1 Focus：当前正在处理的创作焦点

Focus 至少区分：

- `location`：用户所处项目/场景/镜头路径，用于标题与返回；
- `subject`：当前查看的具体对象，如图片版本、视频 TAKE、生成草稿；
- `selection`：暂时选中的候选，不等于已采纳；
- `target`：下一次操作成果准备归入何处，如 Shot 的视频候选；
- `returnAnchor`：发起操作前的位置、滚动锚点、选中项、所开页签。

**规则：** `selection` 不允许被误当作“采用”；`target` 必须在提交前冻结；`returnAnchor` 不决定事实源，只负责交互恢复。跨项目使用资产时，明确展示“用于项目 A / 镜头 03”。

### 5.2 Intent：用户此刻想做的动作

按用户语言组织 Intent：**生成图片、制作视频、修图、选用到镜头、比较、另试一版、修改导演意图、导出、请 Agent 协助**。不在 UI 暴露 `draft.createVideo`、`shot.selectOutput` 等命令名。

每个 Intent 描述所需输入、可用能力、是否有费用、执行边界、完成后应当看见什么。相同意图可以由工具栏、长按或 Agent 卡片触发，但最终都进入同一业务命令。

### 5.3 Surface：承载任务的交互工作表面

| Surface | 适用 | 行为约定 |
|---|---|---|
| 主对象页面 | 项目、镜头、素材、画面 | 只有一个主焦点，保持可见 |
| Quick Sheet | 1–3 项简单选择、短确认 | 不覆盖主体过久，不容纳长表单 |
| Editor Sheet / 抽屉 | Prompt、常用参数、参考列表 | 保留对象预览摘要；键盘出现后自动调整 |
| Fullscreen Task | 长剧本、蒙版、A/B、复杂分镜、长对话 | 全屏单任务，明确完成/返回，不叠第二层工作表面 |
| Picker | 从本项目/全部资产选版本 | 选完返回原任务；保留已选内容、原滚动位置 |
| Activity / Result Tray | 异步进度、候选和待审核 | 非阻断、可稍后处理；不可抢占用户当前输入 |

### 5.4 Return：操作返回原焦点，而不是猜测返回栈

交互返回要遵守优先级：

1. 软键盘存在且焦点可安全释放：优先按 Android 行为收起键盘；
2. 有打开的 Sheet/Picker：关闭当前表面，保留草稿；
3. Fullscreen Task：先做未保存变化保护，再返回原对象；
4. 普通页面：返回真实来源（含从通知/深链接进入的情形）；
5. 来源不存在：回退到对应项目/素材/手工工作台安全入口。

不要只依赖 `router.canGoBack()` 来代表用户真实业务来源。可以用受控的来源描述 + 路由历史，保存 `projectId / shotId / draftId / versionId / localViewKey` 等稳定标识；不在 URL 放 API Key、完整 Prompt 或巨型 Base64。

## 6. 一条具体用户流程：从镜头生成视频并采纳

**目标：** 用户在一个 8 镜头的短片中，看到镜头 03 已选定的分镜图，生成两个 H3 视频候选，并采用第二个。

```text
项目 → 镜头列表 → 镜头 03（当前焦点）
   ├─ 主画面：分镜图、镜头意图、参考摘要
   └─ 主操作「制作视频」
          ↓（带入 projectId、shotId、精确分镜版本、returnAnchor）
      视频工作台：参考已准备 → 编辑动作/时长 → 预检与费用确认
          ↓
      任务已受理：工作台可离开；镜头 03 显示“视频生成中”
          ↓（后台下载与归档，不自动改“选定视频”）
      本镜头候选区出现 TAKE 01、TAKE 02；未选定
          ↓
      用户点 TAKE 02：预览 → 对比 →「采用到镜头 03」
          ↓
      镜头卡更新为“已采用视频”；可继续修改或进入下一个镜头
```

### 6.1 逐步交互规格

| 步骤 | 屏幕主要可见内容 | 主要操作 | 不应发生 |
|---|---|---|---|
| 镜头页 | 当前图、用途标签、制作意图、参考 | 制作视频 | 不展示全部 H3 高级字段 |
| 视频准备 | 固定参考图、动作/运镜、时长、工作流 | 预检并生成 | 不自动换用最新角色/图片版本 |
| 确认 | 服务商、次数、费用/未知费用、目标镜头 | 确认生成 | 不隐式重复提交 |
| 运行 | 本次任务状态、可继续编辑提示 | 继续其他工作 | 不阻塞全 App；不假造进度 |
| 候选 | 可播放视频、TAKE 计数和效果比较 | 采用此 TAKE | 不把浏览预览变成采用 |
| 完成 | 镜头已采用、版本引用、下一镜头 | 下一镜头/继续修改 | 不要求用户先去素材库查找成果 |

### 6.2 特殊场景

- 若用户等待期间正在修改下一次 Prompt：**任务完成提示不自动覆盖编辑区**，使用小结果入口/候选托盘提醒。
- 若任务进入 `UNKNOWN`：提示“结果待核查”，只允许核查原任务；主动新生成是另一个需要确认费用的意图。
- 若原件下载失败但远端生成已成功：展示“已生成，原件待恢复”，按钮是重试归档/下载，而不是重新生成。
- 若返回时草稿未保存或跨入口已修改：保留本页输入，提供冲突恢复，不能静默覆盖。

## 7. 关键屏幕线框：从“按钮列表”转向“主画面 + 决策区”

以下示意优先描述**信息层级与可操作性**，不是最终视觉稿。颜色、圆角和动效应沿现有主题；不要借设计改造强迫替换品牌风格。

### 7.1 手工快速创作（允许无项目）

```text
┌────────────────────────────────┐
│ 手工 ▾     图片创作       任务 • │  ← 简洁工作区标题
├────────────────────────────────┤
│ 个人创作  /  最近生成 v6         │  ← 上下文锚点
│                                │
│          当前画面 / 结果         │
│        点击全屏 · 左右换候选      │
│                                │
│   [候选1] [候选2] [候选3] ...     │
├────────────────────────────────┤
│ 画面描述：夜空中舞者降临…        │  ← 输入摘要；点击完整编辑
│ 模型 V5  · 横屏  · 1 张 · 更多设置  │
│                                │
│ [辅助建议]         [生成图片]    │  ← 稳定底部操作区
└────────────────────────────────┘
```

- 没有生成结果时，预览只占有限高度，立即可见描述输入；有结果时放大画面比例。
- 当用户正在持续出图时，“生成图片”始终可达；已生成结果的“保存/制作视频/比较”在结果工具栏或点开候选后提供，不强迫跳转资产库。
- 顶部“个人创作”可切换项目归属，但不能静默把已有已提交生成改为其他项目。

### 7.2 项目镜头焦点（为今后分镜、TAKE 扩展预留）

```text
┌────────────────────────────────┐
│ ‹ 影片 A / 场景 02        ···    │
│   镜头 03/08  · 角色降临         │
├────────────────────────────────┤
│                                │
│            选定分镜图           │
│              16:9              │
│                                │
│ [分镜]    [视频 2 TAKE]  [声音]  │  ← 只作为内容维度
│ 角色 C01-v3   场景 E02-v2        │
│ 运镜：低机位 → 缓慢推近          │
├────────────────────────────────┤
│ [导演设置] [AI 协助] [制作视频]  │
│      ‹ 上一镜头   下一镜头 ›     │
└────────────────────────────────┘
```

- 分镜/视频/声音是当前镜头的不同**内容层**，而非再建三个一级页面。
- 当视频已生成且待采纳时，同一个主操作位置变成“审阅视频”；用户采纳后变成“继续下一镜头”或“预览片段”，**位置稳定、标签清楚**。
- 任何改变了资产归属或镜头采用的动作，都应带上对象名称和影响范围；“预览此视频”绝不等价于“采用到镜头”。

### 7.3 视频生成：只显示目前真正需要填写的内容

```text
┌────────────────────────────────┐
│ ‹ 镜头 03 / 制作视频      ···    │
├────────────────────────────────┤
│ 参考图：舞者分镜 v3   [更换]      │
│ [缩略] [缩略] [ + ]  音频 0/3    │
│                                │
│ 动作和镜头                      │
│ 「缓缓下降，镜头低角度推进…」     │
│                                │
│ H3 · 10 秒 · 横屏 · 768p   ›      │  ← 常用参数摘要
│ 高级选项：已使用 2 项          › │
├────────────────────────────────┤
│ 预计费用：…  / 暂无法估算        │
│                  [确认并生成]   │
└────────────────────────────────┘
```

用户要的是“让这个镜头动起来”，不是把当前工作流里全部 JSON Schema 字段按顺序填完。低频输入放入自适应表单，只有当前模型支持的选项才出现。高级选项不应隐藏已设置值：折叠后摘要显示“已启用参考运动 / 固定 Seed”之类状态。

### 7.4 结果托盘：不强占正在进行的创作

当模型完成时，当前画布/输入保持不变；底部显示小型“2 个视频候选就绪 · 查看”入口。打开后托盘包含候选缩略图、播放与对比、主操作“采用到镜头 03”。如果用户关闭托盘，结果仍可从镜头/创作记录恢复。

**关键：** 不把“自动保存到 CAS”“导出到相册”“采用到镜头”三个动作揉成一个“保存”按钮；可分别显示“已加入作品库”“保存至手机”“用于镜头”。

## 8. 操作优先级：一个主槽位，但不独裁式隐藏功能

“一屏一个主动作”不能机械执行。创作者可能希望反复修改 Prompt，而不是始终被引导去下一阶段；专业用户也需要并行选择“修图/制作视频/导出”。因此推荐 **一主两辅 + 可发现的工具抽屉** 作为默认预算，而不是全 App 的硬性按钮个数限制。

### 8.1 状态与动作矩阵

| 当前焦点与事实状态 | 主操作（稳定位置） | 直接次操作 | 更多/高级 | 反例 |
|---|---|---|---|---|
| 独立图像草稿可编辑 | 生成图片 | AI 完善描述 | 角色、参考、采样、版本 | 不强迫先建项目 |
| 镜头无分镜候选 | 制作参考图 | 从资产选择 | 导演设置、批量制作 | 不在主屏列出全部模型 |
| 有多个分镜候选、未选定 | 审阅并选择 | 重新生成 | 对比、参数、删除 | 浏览候选不自动采用 |
| 已选分镜、未有视频 | 制作视频 | 修改分镜 | 参考、音频、镜头设定 | 不先跳转到“视频模块首页” |
| 视频正在生成 | 继续其他工作 | 查看进度 | 核查、任务详情 | 不显示假的 ETA；不阻塞镜头操作 |
| 视频候选待审核 | 采用此 TAKE | A/B 比较 | 复用参数、另试一版 | 不因为任务完成就标“镜头完成” |
| 已采用 TAKE | 下一镜头 / 预览片段 | 重做此镜头 | 历史 TAKE、导出 | 不删除旧版本 |
| Agent 修改建议就绪 | 查看并审核 | 拒绝 | 变更详情、讨论 | 不由 Agent 自批自改 |
| 结果状态 UNKNOWN | 核查原任务 | 返回编辑 | 查看原始请求与凭据状态 | 不把“重试”直接连到付费 POST |

### 8.2 动作稳定性约束

- 主操作所在位置固定在当前工作表面的底部安全区；**状态变化可以改变标签，但不能突然把不同性质的动作塞到原位置且不提示**。
- 用户正在写 Prompt、观看视频或对比候选时，后台状态更新只增加提示，不强制切换页面或打断焦点。
- 操作被禁用时应解释原因，如“缺少参考图”或“工作流不支持 15 秒”；禁止仅呈灰色没有文案。
- 经常用的“切换图片/视频”“打开历史”“更换参考”必须有明确可见入口。长按和手势可以加速，但不能成为唯一入口。
- 动作列表由 **意图与真实能力** 决定，而不是根据模型名称到处写散落的条件分支；例如不支持局部重绘时不展示“局部重绘”。

## 9. Sheet、键盘、导航与手势：建立单一表面调度规范

### 9.1 表面不能无限叠加

`ImageDraftScreen` 当前同时可能涉及编辑抽屉、AI 助手、处理 Sheet、图片预览、历史，`VideoDraftScreen` 也有工作流/方向/时长/设置/素材选择。此处最需要统一的是**并发规则**，而非再发明一个不同形态的弹窗。

建议每个工作区仅有一个 `activeSurface`，其候选类型为：`none | quickSheet | editor | fullscreen | picker | agent`。允许主内容背后继续保留，但不允许两个需要输入的表面同时争夺焦点；确需串行打开时用受控转场（例如关闭“更多设置”后打开“参考素材选择器”），不能靠多个布尔值偶然共存。

### 9.2 键盘交互协议

1. 键盘出现时，标题栏压缩至必要对象摘要，预览可以收缩或隐藏；当前输入和确认动作不能被键盘挡住。
2. 从长 Prompt 弹到 Agent 建议时应先保存或保持可恢复的编辑快照，避免切换焦点丢字。
3. `Back` 首次收键盘、再次关闭编辑表面、最后离开工作区；除非有未保存变更保护，不能连续弹多次重复确认。
4. 对长文本使用独立全屏编辑，避免在半屏 Sheet 中编辑数十行 Prompt。返回时展示“已更新草稿”，而不是重建工作区。
5. 适配字体缩放到至少 1.3x、系统手势导航和折叠/旋转；只缩小图标绘制不缩小可点击范围。

### 9.3 推荐的表面类型与触控尺寸

- 主操作按钮：建议可点高度约 48–56dp，文字可见，远离系统手势区。
- 普通功能行和图标：建议可点区域至少 44–48dp；图标本身可较小，但命中区域不可跟着缩到 34dp。
- Quick Sheet：2–6 个小选项、短确认；大批选项改为独立选择器，不在底部塞巨大列表。
- Editor Surface：承担具体任务的参数输入，并且有明确的“完成/收起”路径。
- 全屏：蒙版、长 Prompt、分镜精细编辑、详细 A/B、长会话；全屏和底部 Sheet 不应彼此无限嵌套。

具体尺寸是设计目标而非 Android 强制规范；最终需结合无障碍和真机验证。

### 9.4 折叠屏不是简单“放大手机”

| 可用宽度 | 主要布局 | 次级表面 | 返回规则 |
|---|---|---|---|
| Compact：小于 600dp | 单主内容区，局部覆盖工具，底部动作 | Sheet / 全屏 | 逐层关闭至原焦点 |
| Medium：600–839dp | 媒体主区 + 可选侧栏 | 侧栏或底部 Sheet | 主区持续可见，选项切换不重建内容 |
| Expanded：840dp 及以上 | 列表 / 内容 / 工具可分栏 | 持久工具侧栏 | 折叠回手机时保留焦点、选中项和草稿 |

窗口宽度应来自实时可用空间，而非判断手机型号。折叠屏从内屏切回外屏时，底层选中的 Shot/AssetVersion 不得改变；只有显示方式变化。

## 10. 资产关系如何在交互层“自然出现”

不要把复杂的版本关系逐一翻译成“加入项目”“固定版本”“设为默认”“设为镜头参考”“从项目移出”等多排按钮。它们应该由用户明确的**使用意图**触发，并在必要时提供影响范围说明。

### 10.1 三个视图，同一份数据

1. **项目中的素材**：展示本项目角色、场景、分镜和视频成果，面向“当前要使用什么”。
2. **全部资产库**：搜索、筛选、跨项目复用，面向“我以前做过什么”。
3. **使用位置与来源**：打开素材后反查所用项目/镜头及版本关系，面向“这次修改会影响哪里”。

同一资源只有一个逻辑资产与一个或多个不可变版本；这三种视图只是查询结果，不需要新的文件夹或二进制副本。

### 10.2 资产选择器的目标是“选定用途”，不是“管理资源”

从镜头点“更换参考图”时，选择器顶部应写 **“为镜头 03 选择参考图”**，默认筛选本项目的图片，并允许切换到全部资产。选择一张图后，显示“图片 A · 版本 3”，确认则建立准确引用并返回镜头。若要选择多个图，展示数量约束与可调整顺序。选材过程不自动设置素材默认版本或改变其他镜头。

采用明确的两层语义：**预览选中 → 确认用于目标**。对多图允许批量确认；一张图可能被多个镜头复用，不复制原件。对于已在项目中使用的资产，显示“已在 3 个镜头使用”作为可选详情，而非阻挡选材。

### 10.3 版本采用：三个范围必须说人话

| 技术事实 | UI 推荐语义 | 适用位置 |
|---|---|---|
| Asset currentVersionId | 默认展示版本 | 资产详情与全部资源库 |
| Project pinned version | 本项目使用的版本 | 项目资源列表、角色设定引用 |
| Shot selected version | 此镜头采用版本 | 分镜候选、视频 TAKE 审阅 |

用户只在改变这些关系时才需要知道其区别。例：“将当前图片用于镜头 03（固定版本 3）。不影响其他镜头。”而不是让用户理解 ID、pin 与 version relation。

### 10.4 候选托盘是“资产机制”与“创作行为”的边界

借鉴 InvokeAI 的 staging：生成完成的候选可以查看、比较、保留，但**默认不等于采用**。候选所在的项目/镜头在任务创建时已经记录；用户选用某个候选后，更新目标镜头的采用引用；任务/文件来源保持不变。

这样才能支持长篇制作中的反复试镜头、不同角色姿态、多 TAKE 比较，并避免 AI 自动替换已批准画面。

## 11. Agent 的位置：交互层助手，不是另一套创作宇宙

### 11.1 两类 Agent 体验

**全屏 Agent 工作台**：用于构思、跨场景规划、长链路任务与记录查阅；支持项目范围、长会话和真实任务卡片。

**上下文 Agent Surface**：从镜头、草稿、分镜、结果版本唤起，保留当前对象与选择；适合“让这个镜头更有压迫感”“为这组图片整理相同风格的 Prompt”。它默认只读取当前对象必要上下文；若要扩大到其他项目，需要明确切换。

上下文 Agent 不必创建新的“第二个助手”后端。共享已有 DeepAgents/AG-UI、创作工具与命令回执，差异在启动上下文、显示尺寸和工具能力白名单。

### 11.2 建议的 Agent 结果交互

```text
镜头 03 → AI 协助：增强压迫感
  → Agent 提议修改：机位 / 运镜 / 光线
  → 卡片展示“修改前 → 修改后”，可逐项编辑
  → [采用修改] / [继续讨论] / [拒绝]
  → 更新镜头导演意图，保留原工作页与历史
  → 如需付费生成，另出现具体提交确认
```

**生成建议**与**执行生成**之间必须有权限边界。Agent 给出 Prompt 不等于任务已执行；工具返回 `completed` 不等于视频已下载/可用于镜头。业务卡片应关联真实 CommandReceipt、Job、AssetVersion，并按事实刷新。

### 11.3 不要用聊天替代所有直接操作

频繁的确定性操作（选图、比较 TAKE、修改时长、切换素材版本）应当直接点按完成。Agent 用于模糊意图、复杂组合决策、批量规划以及专业知识解释。否则所谓“免按钮”只是把原本一次点击变成数轮对话。

## 12. RN 实现建议：最小契约、增量改造、避免通用框架过度设计

这里的示例是**交互层接口草案**，不是新数据库 schema，也不代表分支已有这些类型。目的在于让多页面之间有同一种返回和上下文理解。

### 12.1 建议的 TypeScript 契约

```ts
type FocusRef =
  | { kind: 'personal'; draftId?: string }
  | { kind: 'project'; projectId: string }
  | { kind: 'shot'; projectId: string; shotId: string }
  | { kind: 'asset'; assetId: string; versionId?: string };

type CreationIntent =
  | 'generate-image' | 'generate-video' | 'edit-image'
  | 'review-candidates' | 'adopt-to-shot'
  | 'compare-versions' | 'edit-direction' | 'export';

type ReturnAnchor = {
  route: string;                 // 应为允许列表中的已知路由
  focus: FocusRef;
  localViewKey?: string;         // 场景、页签、版本或列表位置
};

type CreativeLaunch = {
  focus: FocusRef;
  intent: CreationIntent;
  sourceVersionIds?: string[];   // 明确的精确版本
  returnTo?: ReturnAnchor;       // 导航恢复；不影响任务事实
};

type ToolSurface =
  | 'none' | 'quick-sheet' | 'editor'
  | 'picker' | 'fullscreen' | 'agent';
```

**约束：** 与业务有关的 `projectId/shotId/assetVersionId` 由现有命令服务重新校验；UI 不能因为拿到了 `CreationLaunch` 就绕过项目范围和资产权限。跨进程恢复应使用稳定对象 ID，不依赖 RN 组件闭包。路由参数必须进行大小和取值校验。

### 12.2 共享工作区外壳，而不是共享一个巨大页面组件

```text
CreativeWorkspaceShell
├── ContextHeader      当前创作对象、模式、返回和任务状态
├── FocusStage         画面/视频/分镜/剧本的主内容
├── ContextActionBar   1 主 + 0–2 常用次操作 + 工具入口
├── SurfaceHost        统一 Sheet / Picker / Fullscreen 调度
├── ContextAgentHost   项目/镜头/草稿级助手
└── ActivityAnchor     真任务与候选提醒，不抢编辑焦点

现有业务组件继续使用：
ImageDraftScreen / VideoDraftScreen / ProjectShots /
CreativeResults / ImageEditorDrawer / CreativeAssetPicker
```

不建议把各业务组件全部塞进新的单个 5,000 行“总工作台”。Shell 只负责导航、焦点、表面互斥和动作槽位；生成字段、参考约束、版本选择仍由现有领域组件提供。

### 12.3 Actions 不是静态全局菜单

`getAvailableActions(focus, capabilities, state)` 返回动作**描述符**，但不要使用无类型的字符串动态执行器。业务实现仍由各功能模块显式注册/装配，UI 仅利用其 `id、label、enabled、reason、priority、surface` 决定呈现。只有真正拥有实现的能力才进入菜单。

主操作的选择顺序推荐：用户显式正在执行的任务 ＞ 当前对象待审核/受阻事实 ＞ 当前阶段的建议下一步。不能让模型文本直接改变主按钮，也不能让后台下载完成打断用户正编辑的下一版。

### 12.4 推荐拆分点与兼容策略

- `CreativeHome`：收敛顶栏；生成历史和任务入口位置保持可见；保留现有草稿恢复。
- `ProjectShots`：添加“镜头焦点页”路由；原镜头卡先减少重复操作，再逐步转接详情页，避免一次性重写镜头列表。
- `ImageDraftScreen` / `VideoDraftScreen`：支持可选 `CreativeLaunch`，先统一来源与返回，再改视觉外壳；不得混淆已提交和下一次可编辑草稿。
- `CreativeResults`：先区分“预览、保存、镜头采用、继续生成”的目标，再调整工具分组；可保留旧控件作为兼容入口一段时间。
- `AgentWorkspace`：从对象唤起时恢复同一会话/对象范围；全屏 Agent 保留项目级能力；避免把现有项目会话在后台悄悄重绑定。
- `WorkbenchUI`：保留已有 ParameterSheet 的业务调用，逐步引入统一 `SurfaceHost`；不要为了统一而同时保留两层模态导航。

## 13. 性能是交互系统的一部分，不是后端附注

最新仓库报告 `docs/reviews/2026-10-28-performance-audit.md` 中，F03–F08 对结果、版本、详情和 Agent 卡片提出了优先级较高的增长风险。本报告不重复其底层修复细节，但将其转成 UI 交付门槛：

| 高版本量场景 | 必须匹配的 UX 设计 | 必须配套的查询/渲染约束 |
|---|---|---|
| 300 个历史结果版本 | 只显示最近候选与分页历史；不能一次挂载全部 | 版本分页、轻量元数据摘要、可见性驱动刷新 |
| 200 个视频缩略图 | 虚拟化网格、惰性封面、稳定宽高 | `FlatList` 或等效虚拟化、缩略图缓存、批量查询 |
| 多素材选择器快速搜索 | 搜索时保持焦点、少量筛选；不每次打开大详情 | 索引/分页/输入防抖、按页加载与取消旧请求 |
| 同一版本被多处引用 | UI 显示同一结果、不重复解码大图 | 复用封面缓存与已获取的摘要，不每卡重复读全部 versions |
| 生成中同时选材 | 任务进度独立、选材不卡顿 | 原生线程、慢网络与文件校验隔离；后台任务不垄断关键路径 |

不要在 React 组件里每隔 2 秒扫描整个资产版本表，然后通过视觉动画掩盖问题。任务轮询、资产浏览和生成执行应有各自的可见性与刷新策略；结果事实由现有数据库/执行器提供，UI 层订阅或按需查询。

**性能验收建议：** 在 100/300/1000 资产版本规模的合成数据下，分别记录首次打开、搜索响应、快速滚动、图片切换、Sheet 打开与返回；记录设备型号、内存、缩放倍率、平均/95 分位耗时和掉帧。没有测量数据前，不写“已解决卡顿”。

## 14. 分阶段改造方案（先验证流，再统一组件）

### 阶段 0：UX 基线与故障归档（P0）

**改造前先做**：固定当前分支 APK 与录屏，覆盖 360–400dp 常规手机和折叠屏；分别完成快速出图、图转视频、镜头选 TAKE、Agent 修改建议四条任务。记录操作点击、跳转/回退次数、键盘/弹层冲突与耗时；不能凭印象推断。

交付：基线任务脚本、入口地图、操作密度清单、已知缺陷列表、真实录屏证据。可由一名开发者和 2–3 名内部试用者完成预检，后续扩大样本。

### 阶段 1：一条完整“镜头 → 视频 → TAKE”纵向样板（P0）

优先改 `ProjectShots` → 镜头焦点页 → `VideoDraftScreen` → `CreativeResults`，让来源、目标、返回明确。先复用当前业务命令，不引入泛化多智能体流程与新媒资体系。

验收：一个镜头的参考图版本在生成前后不漂移；生成中可返回；候选归属原镜头；采纳显式确认；恢复 App 后仍找到对应工作位置；异常不会触发额外消费。

### 阶段 2：统一工作表面与操作槽位（P0/P1）

抽出 `ContextHeader / ContextActionBar / SurfaceHost`，先在图像和视频工作台试点。解决顶栏重复动作、互相竞争的 Sheet、键盘覆盖和多状态按钮。完成后再迁移资产详情、版本比较。

验收：任一时刻只有一个主动编辑表面；系统返回可预测；草稿不会被误丢；主操作始终可读；字体缩放与单手操作可达。

### 阶段 3：资产选择与候选审阅体验（P1）

升级 AssetPicker：缩略图、项目/全局范围切换、搜索筛选、精确版本及使用目的；结果托盘增加“只浏览/比较/采用”清晰语义。同步处理上述高版本量性能风险。

验收：同一参考图跨两镜头使用不复制原件、不改原镜头；数百素材下选择仍可操作；单次生成多候选均可找到且无需打开原生文件管理器。

### 阶段 4：上下文 Agent 与可审核提案（P1）

从镜头/草稿进入 Agent，显示对象锚点，返回原内容；建议卡可审查/应用；生成授权与提交区分；不重建已有 LangGraph/AG-UI 运行时。

验收：Agent 失败不冒充成功，应用变更可以看到前后内容，聊天结束不取消已提交任务，项目范围切换不串数据。

### 阶段 5：折叠屏、大规模素材及后续专业能力（P2）

在上述契约稳定后再做双栏、镜头序列、Animatic 和复杂分镜。横向自适应是相同对象/动作在不同宽度下的呈现，不是第二套业务流程。

### 14.1 建议 PR 切分（每个 PR 可独立回归）

| PR | 最小变更 | 主要文件 | 验收重点 |
|---|---|---|---|
| UX-01 | 交互上下文与返回锚点，纯类型/导航测试 | `creative/` 新契约、路由适配 | 深链接/普通返回/草稿恢复 |
| UX-02 | 镜头焦点页及项目镜头卡入口 | `ProjectShots.tsx`、新增 Shot 页面 | 镜头上下文稳定、主动作正确 |
| UX-03 | 视频工作台携带来源/目标并返回 | `VideoDraftScreen.tsx`、`WorkbenchScope` | 不改变提交/归档事实 |
| UX-04 | 结果候选与采用体验 | `CreativeResults.tsx`、候选浏览组件 | 浏览≠采用、重复点击幂等 |
| UX-05 | 工作表面互斥、顶栏与键盘规则 | `WorkbenchUI.tsx`、Image/Video 工作台 | 关闭层级、触控尺寸、字体适配 |
| UX-06 | 选材器与素材列表的分页虚拟化 | `CreativeAssetPicker`、AssetTile/数据摘要 | 300+ 版本滚动与搜索 |
| UX-07 | 上下文 Agent 建议/返回 | `AgentWorkspace`、Agent 卡片 | 同源命令、权限与修订冲突 |

不建议 PR 一次性覆盖全部一级导航、所有 Asset 页以及 Agent 运行时。每一步必须保持当前“独立生成一张图”和“查看历史作品”可用。

## 15. UX 验收指标与用户测试计划

### 15.1 待验证的目标（不是当前实测结论）

| 指标 | 初期建议目标 | 数据来源 |
|---|---|---|
| 四条代表任务的完成率 | 试点中 ≥ 90%，失败必须分类 | 受控用户测试 |
| 用户能说清当前对象与输出去向 | ≥ 90% 的测试任务能正确复述 | 操作后简短询问 |
| 关键动作发现时间 | 第一次使用可在 10 秒内找到主操作 | 录屏计时 |
| 由镜头进入生成再返回 | 不需要重新选项目/镜头/参考图 | 路由与持久化断言 |
| 候选浏览误触采用 | 0 次错误采用 | 功能测试 + 试用录像 |
| 应用退后台/重启恢复 | 草稿、引用、任务状态保持一致 | RN/Android 仪器回归 |
| P95 素材选择反应时间 | 与设备/数据集一起设阈值，目标先测后定 | 性能埋点与 Perfetto |
| 大字号、折叠、键盘 | 主操作与当前输入可达，无遮挡 | 多设备矩阵 |

**注意：** “完成率 90%”“10 秒找到主操作”是拟定质量门槛，绝不是本项目已达到的指标；真机基线测出后应有依据地调整。

### 15.2 任务脚本（每条都能复测）

- **T1 快速出图**：从冷启动输入一个描述，生成并修改第二版，再保存到相册；不创建项目。
- **T2 镜头制作**：项目 S02-03 选定一张已有参考 → 生成视频 → 离开等候 → 返回审阅 → 采用 TAKE；任务无法确认时核查原任务。
- **T3 资产复用**：从本项目选择一张图片版本用于另一镜头；验证原镜头不变，使用位置能反查。
- **T4 Agent 修改**：在镜头页提出“增强压迫感” → 看变更提案 → 应用或拒绝 → 返回镜头，人工修订期间发生冲突时不覆盖。
- **T5 系统扰动**：在每条任务的输入中途分别模拟键盘、旋转、前后台、来电/进程终止、网络断开和大字体。
- **T6 规模压力**：将资产库扩展为 100/300/1000 个版本或条目，重复选材、版本对比、返回、Agent 结果预览。

### 15.3 建议记录的埋点（本地、非敏感）

`screen_enter、focus_change、surface_open/close、primary_action_exposed/clicked、back_transition、picker_complete、draft_resume、candidate_preview、candidate_adopt、agent_proposal_review、task_result_open`。

只记录对象类型、页面、耗时、成功与错误码等必要字段；不记录完整 Prompt、图片内容、Token 或敏感用户素材。原始录屏须经过用户授权并在可控环境留存。让指标服务于 UX 研究，不为测量额外引入联网遥测依赖。

## 16. 容易走错的五条路线与取舍边界

1. **把所有入口改为聊天。** 会增加高频确定性操作的对话成本，也降低专业用户的可控性。Agent 应降低复杂任务门槛，不替代简单触控。
2. **让一个无限画布承载所有内容。** 桌面适用，但对窄屏手机的精确连接、选择和缩放成本很高。可以在宽屏/预演中提供概览，但首期仍以对象焦点页为主。
3. **为了统一而合并所有编辑器。** 图片蒙版、视频参考、长文本和剪辑时间线有不同交互规律；共享 Shell，不共享成一个巨大表单。
4. **把所有功能藏进一个“更多”。** 表面按钮少了，却造成低频与高频入口混乱。统一按操作频率、上下文和风险分层，保持高级功能有清楚的发现路径。
5. **过度“智能”地自动采用或切换页面。** AI 和任务系统可以提出下一步，但不能擅自改变作品选定版本、触发未知费用或夺取正在编辑的焦点。

**不建议在本轮实现的内容：** 完整 NLE 剪辑器、通用节点画布、云端多人协作、替换 DeepAgents runtime、重新设计 CAS 与 Job 内核、全 App 视觉品牌重构。这些都可能有长期价值，但不能解决眼下最核心的移动交互连续性问题。

## 17. 最终建议与设计决策记录

### 决策 D1：保留双工作方式，不再增加永久顶级导航

沿用已实现的“手工 / Agent”，把项目、素材和任务视为共用对象与辅助目的地。评估完成前，不主张直接改为固定三或四个底栏 Tab。

### 决策 D2：建立 Focus–Intent–Surface–Return 最小协议

任何新能力先回答：作用于谁、用户想完成什么、用哪种工作表面、结束后回到哪里。没有这四项说明的功能不进入主工作区。

### 决策 D3：镜头页成为影视制作的最小垂直样板

优先改造一条「镜头 → 视频 → TAKE 审阅 → 采用」流程。验证后再扩展角色、场景、分镜和粗剪，避免先造一套未被实际创作检验的导航系统。

### 决策 D4：保持业务事实与 UI 暂态隔离

UI 的暂时选中与 Sheet 状态可以消失或恢复；已提交任务、不可变版本、项目/镜头采用和 Agent 授权必须继续依赖现有持久系统，不能由新的全局 UI store 成为事实源。

### 决策 D5：规模性能进入 UX 验收门槛

先优先解决高版本量下的全量轮询、重复校验、虚拟化与快速检索问题；“一站式工作台”首先要保证创作者能迅速看见和选择作品。

### 结语

**现在的核心不是“手机屏幕太小，所以必须藏更多功能”，而是“功能需要围绕正在创作的对象，被正确地组织、触达、执行和返回”。**

如果把这套契约建设好，你未来添加角色圣经、自动分镜、Seedance、复杂生成工作流、Agent 制片、TAKE 审阅乃至 Animatic 时，都只是在稳定交互体系中增加新的 Intent/Surface，而不是不断增加新的一级入口、重复弹层和跨页面跳转。
